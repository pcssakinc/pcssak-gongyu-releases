# PCssak Gongyu 0.3.3 — 지금 이 PC에서 멈춘 이유부터 살피는 변경일기

## 무료 Early Access — 실패 기록을 남기고 확인 범위를 넓혔습니다

0.3.2를 공개한 뒤 직접 시험한 PC에서 SSH 켜기가 다시 멈췄습니다. 기존 설치는
알아봤지만 방화벽 규칙을 처리하던 84%에서 `native_method_output_null`, `HRESULT=0`이
나왔고 실패 후 원복 검증도 끝나지 않았습니다. 다시 켜기를 누르면 2%에서
`LEGACY-RECOVERY`로 중단됐습니다. 자동 시험과 공개 파일 검증은 통과했어도 실제로
사용하던 PC의 문제가 해결된 것은 아니었습니다. 이 실패를 이전 성공 기록으로 덮지 않습니다.

이번 0.3.3은 이 실패에서 확인한 **결과 검증·기존 기록 대조·진행 안내**를 보완합니다.
자동 시험에서 확인한 수정과 실제 PC에서 확인한 결과를 나누어 기록합니다. 모든 환경의
문제가 해결됐다고 약속하지 않으며, 실제 설치·복구·접속은 별도 실기 기록을 따릅니다.
0.2.9·0.3.0·0.3.1은 비공개 시험본이었고 이미 공개한 불변 태그·자산·노트는 교체하지 않습니다.

제공 여부는 버전 고정 GitHub 릴리스와 검증된 9자산이 기준입니다. 게시 전에는 같은
최종 소스의 14단계·설치본 대조·두 업데이트 서명·9자산 검증을 완료하고, 게시 뒤에는
공개 파일과 홈페이지의 버전·해시를 다시 확인합니다. 아래 변경 설명이나 이전 검사 결과가
이 게시 증거를 대신하지는 않습니다.

## 1. 빈 결과 객체를 오류 코드 하나로 끝내지 않고 실제 목표 상태를 확인합니다

Windows가 요청 완료를 알려도 방화벽 제공자가 결과 객체를 돌려주지 않는 경로가 있습니다.
0.3.2는 이 경우를 별도 오류로 구분했지만, 실제 목표 상태를 확인해 마칠 수 있는 고정
방화벽 전환도 거부했습니다. 그렇다고 코드 0이나 빈 객체를 성공으로 바꾸지는 않습니다.

정확한 방화벽 규칙의 `Enable` 또는 `Disable`만 정해진 방식으로 한 번 요청합니다.
완료 상태가 확인되고 명시적 오류가 없는 경우에 한해, 결과 객체가 없더라도 같은 규칙의
정확한 ID·전체 정책·목표 활성 상태와 호출자 보호 조건을 다시 읽어 모두 확인한 뒤
완료를 판정합니다. 결과가 비었다는 이유로 변경 명령을 다시 보내지 않습니다.

요청·완료 조회 실패, 시간 초과, 잘못된 반환값이나 자료형, 명시적 Windows 오류는 계속
거부합니다. 결과 객체가 정상으로 왔어도 마지막 상태 검증을 생략하지 않습니다. 읽기에
실패하거나 대상이 바뀌었거나 기대 상태와 다르면 성공으로 표시하지 않습니다. 이 대안은
고정된 방화벽 활성 전환에만 적용하며 일반 WMI 읽기나 임의 메서드로 넓히지 않습니다.

실패 뒤에는 일부 변경이 남을 수 있습니다. “오류가 났으니 아무것도 바뀌지 않았다”고
추정하지 않고 원상태·복구 장부와 현재 상태를 보존해서 확인합니다.

## 2. 같은 주소를 다르게 적은 기존 기록도 정확히 비교합니다

실제 기존 규칙을 대조하면서 동일한 단일 IPv6 주소를 `/128`로 표현한 경우와
시작·끝 주소가 같은 구간으로 표현한 경우가 다르게 판정되는 경계를 보완했습니다.
실제로 같은 한 주소인지 확인한 표현만 비교 과정에서 동등하게 취급합니다.

더 넓은 네트워크나 서로 다른 주소·정책을 같다고 추측하지 않습니다. 기존 V4 원문·
원래 정책 해시 형식·변경 전 상태·중단 복구 근거를 유지하고, 기존 기록을 새 형식으로
강제 교체하거나 장부 삭제로 검사를 통과시키지 않습니다. 정확한 규칙 ID와 전체 정책
대조, 패키지 규칙 분리와 기존 대상을 포함한 일반 규칙 변경 상한 4개도 그대로입니다.

보완 후 개발 PC의 생산 사전 계획은 정확한 ID 3개·충돌 3개로 통과했고 시스템 쓰기는
없었습니다. 이것은 읽기와 계획 검증의 결과이며 실제 적용·원복·접속 성공을 뜻하지 않습니다.

## 3. 하나도 복구하지 못한 실패도 화면에서 끝난 상태로 알려드립니다

복구가 0/3에서 실패했을 때 계속 기다리는 것처럼 보이지 않도록 실패 종료 상태를
표시합니다. 해당 문구는 10개 언어에 한 키씩 반영합니다. 단계별 처리 건수는 전체
성공률이 아니며, 0건 실패를 일부 성공이나 전체 복구 완료로 바꾸지 않습니다.

이전 원문 복원 전의 오류와 복구 조회·적용 오류를 기록하고 고정된 진단 분류로 나눕니다.
이후 문제를 확인할 때 어느 단계에서 끝났는지 구분하기 위한 변경입니다. 규칙 주소·
개인 경로·계정·공급자 원문을 공개 진단 코드에 넣지 않습니다. 원본 로그는 공개하지 않습니다.

기존 요청 식별자, 시작부터 실제 작업 종료·후속 SSH 상태 조회까지의 중복 실행 차단,
실제 단계·건수·경과 시간 표시는 유지합니다. 화면 취소나 대기 상한은 실제 작업의 강제
취소가 아닙니다. 복구가 끝났다고 SSH를 자동으로 켜지도 않습니다.

## 4. ‘100%’ 안내와 실제 SSH 연결은 별도로 확인합니다

2026-09-15 개발 중 다른 PC의 첫 제보에서 사용자가 확인한 것은 설정 진행이 100%에 도달하고 재부팅 뒤
접속할 수 있다는 안내가 표시된 상태까지였습니다. 당시에는 재부팅하지 못했으며 SSH
로그인 성공을 보고한 것은 아닙니다. 별도 도구의 실제 TCP 22 연결 확인은 시간 초과로 끝났습니다.
화면 진행률·재부팅 안내·포트 연결·SSH 인증·SFTP 성공을 같은 결과로 묶지 않습니다.

이후 사용자는 실제로 재부팅했고 다시 처음부터 SSH를 설정하라는 화면이 나와 버튼을
눌렀더니 새로 설치 중이라고 표시됐다고 알려주었습니다. 처음에는 진행 중이라고 했으나,
이어 84% LAN 규칙 단계에서 다시 실패했다고 보고했습니다. 사용자가 읽은 설명은
기존 방화벽 기록 확인 실패를 가리켰지만 당시 정확한 오류 원문과 근본 원인은 확인되지
않았습니다. 실제 Windows 기능 추가가 다시 실행됐는지와 설치 반복 여부도 확인하지
못했습니다. 화면 표시나 오류 전언만으로 재설치 실행·원인·문제 해결을 단정하지 않습니다.

복구 조회가 복구 불필요를 반환한 읽기 결과도 실제 SSH 연결이나 완전 원복 성공의
증거가 아닙니다. 이전 실패 기록은 보존하고 두 PC의 재부팅·로그인·파일 전송 결과는
확인한 날짜와 대상 범위를 갖춘 별도 실기 기록으로 남깁니다.

코드에서도 설치 뒤 재부팅을 기다리는 경로가 전체 100%와 모든 단계 완료·성공 알림을
표시하던 모순을 확인해 보완했습니다. 이제 응답과 진행 이벤트 모두 OpenSSH 설치 단계가
끝났고 재부팅이 필요하다는 경고로 표시하며, SSH 설정이 아직 미완료임을 알립니다.
재부팅한 뒤 「SSH 접속 켜기」를 다시 실행해 나머지 설정을 마무리해야 합니다. 화면
새로고침이나 재부팅만으로 접속이 준비된다고 안내하지 않습니다. 이 문구도 10개 언어에
반영하며 실제 모든 설정이 끝난 정상 완료 분기는 유지합니다.

새 제보를 따라 확인한 상태 필드의 `installed`는 Windows 서비스 관리자의 `sshd` 등록
여부만 읽고 있었습니다. 이를 선택적 기능 미설치나 처음 사용하는 PC라고 단정하던 문구를
서비스 등록 상태로 좁혔습니다. 실제 기능 상태는 켜기 과정에서 별도로
확인하며, 서비스가 등록됐다는 화면 정보와 전체 SSH 설정 완료도 같은 뜻이 아닙니다.
기능 상태를 읽을 때는 확인 단계로 표시하고 실제 기능 추가 요청 직전부터 설치 진행을
표시하도록 순서를 조정했습니다. 기존 서비스가 있으면 DISM을 생략하는 경로를 유지하고,
기능이 이미 설치됐거나 재부팅 대기 상태이면 기능 추가와 설치 진행 이벤트를 내보내지
않습니다. 실제 DISM 상태·기능 추가 시작·반환 상태는 로컬 진단에 기록합니다. 상태 조회가
값을 반환하지 않았을 때의 기존 추가 정책이나 소유 기록을 바꾸지는 않았습니다.
이 보완은 잘못된 안내를 줄이기 위한 것이며 실제 설치 반복이나 PC2 실패가 해결됐다는
근거는 아닙니다. 실제 재실패의 정확한 로그와 상태는 별도로 확인해야 합니다.

## 4-1. 보호 차단 규칙이 없어졌다는 확인도 오류와 구분합니다

보호 차단 규칙 삭제 뒤 조회에서 어떤 오류든 규칙이 없어진 것으로 판단하던 검증을
좁혔습니다. 해당 규칙 조회가 정확한 파일 없음 코드 `0x80070002`를 반환한 경우만
부재로 확인합니다. 같은 이름의 규칙이 하나라도 남으면 미완료이며 접근 거부·일반 실패·
공급자 조회 오류·다른 찾기 오류는 원래 오류를 보존합니다. 실패를 정상 부재로 바꾸지 않습니다.

기존 동명 규칙 제거 범위와 횟수는 유지하고 삭제를 자동으로 재시도하거나 전체 규칙을
추가 조회하지 않습니다. 실제 보호 차단 삭제나 현재 PC 복구 성공을 이 회귀만으로
확정하지 않으며 기존 설정과 복구 기록 보존을 계속 요구합니다.

## 5. 기존 설치·설정과 업데이트 경로를 보존합니다

정상 수동 SSH의 설정·방화벽·자동 시작 유형을 인수하거나 덮어쓰지 않는 구분을 유지합니다.
PCSSAK 관리형 SSH의 동의·원상태 기록·복구 순서와 일반 규칙의 자동 처리 한계를 유지합니다.
일반 규칙이 5개 이상인 환경의 자동 처리를 허용하거나 다른 제품 설정을 바꾸는 패치가 아닙니다.

설치기는 기존 지원 범위에 **공개 0.3.2에서 0.3.3으로 보호 교체**하는 네 진입 경로를
추가합니다. 백업·중단 복구·수동 설치·재설치 모두 기존 소유 표식과 원래 파일·설정·
공유·SSH 기록을 확인합니다. 교체 실패 시 이전 버전과 복구 근거를 남기고 새 앱 성공으로
표시하지 않습니다. 이전 버전 회귀를 유지하면서 새 분기·상수 누락·잘못된 버전 표기·
교체 실패·다음 실행 복구를 검사하도록 보강합니다. 실제 설치 시험과는 별개입니다.

Cargo와 Tauri 제품 버전, 패키징 SECURITY, README, 한영 사용 설명서와 공개 문서
템플릿을 같은 0.3.3 버전으로 맞춥니다. 기존 `rustls 0.23.45` 보완과 잠금 의존성·법률 정본·
업데이트 공개키는 바꾸지 않습니다. 제3자 고지·MPL 묶음은 최종 잠금과 실제 버전에 맞춰
별도 생성·검증하며, 이번 문서 준비로 생성·검증 완료를 대신하지 않습니다.

- 설치 파일은 `PCssak-Gongyu-0.3.3-Windows-x64-Setup.exe`입니다.

위 파일명과 일치하는 실제 검증·공개 자산이 있을 때만 다운로드·업데이트할 수 있습니다. 정상 동의가 있는 공개
0.2.0~0.2.8·0.3.2 및 비공개 0.2.9·0.3.0·0.3.1의 업데이트 경로를 유지합니다.

0.1.0만 별도 제거 후 설치하며 동의·설치 기록을 확인하지 못하면 대화형 안내를 따릅니다.
